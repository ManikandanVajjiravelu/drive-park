# How we work on Usop

Product and security rules live in AGENTS.md and docs/scenarios.md. This page is the process around them.

## Plan first

Write the plan before touching a file: what changes, which files, how it is verified, how it rolls back.
If the plan cannot name the files, the task is not ready to start.

## Branch, then a pull request

Never commit straight to main. Work on a branch, open a pull request and fill in the checklist in
.github/PULL_REQUEST_TEMPLATE.md. Rewriting published history is banned (see AGENTS.md).

## Checks must be green before merging

`node scripts/check-repo.mjs`, `npx tsc --noEmit` and the tests must pass locally, and Guard plus CI must
be green on the pull request. Never merge with a red check and never disable a check to get through.
`npm run check:repo` runs the same repository checks: tracked secrets, .env files, lockfiles other than
bun.lock, seed/helper scripts, NUL bytes, CRLF in the index, and a migration without a journal entry.

## SQL: test project first, then production

1. Apply every migration to usop-test first, check it, then apply it to usop-prod.
2. Run SQL only through scripts/apply-sql.mjs. Never paste statements into a dashboard by hand.
3. Every `drizzle/migrations/NNNN_name.sql` gets an entry in drizzle/migrations/meta/\_journal.json.
4. Never edit a migration that has been applied. Add a new migration that corrects it.

## Two Supabase projects

- usop-test: seed data, database tests, every migration and every experiment first.
- usop-prod: real user data only. No seeds, no test accounts, no experiments, no direct edits.

## Secrets stay out of chat and files

Never paste a connection string, database password, service key or API token into chat, an issue, a
commit, a doc or a screenshot. Keep them in .env (untracked) or in the CI secret store; .env.example
holds placeholders only. If a secret lands in a file or a message, treat it as leaked and rotate it.

## Do not commit helper or accidental files

No one-off scripts (`seed-*.mjs`, `fix-*.mjs`, `inspect-*.mjs`, `check-*.mjs` at the repo root), no SQL
dumps, no repo-tree.txt, no .env files, no lockfiles other than bun.lock, no files generated by accident.
scripts/check-repo.mjs fails the build for all of them.

## One writer on the repository

One person writes to the repo. No Lovable bot pushing on top of hand-made changes, no two agents in the
same files, no parallel pushes to one branch. Keep the connected branch working at all times.

## Rotate keys after any exposure

Any key that appeared in a file, a commit, a chat message or a screenshot is compromised. Rotate it in
Supabase and at the provider (Razorpay, email), update the secret store, redeploy, confirm the old key
is dead, and only then continue with the next change.
